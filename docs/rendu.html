3. Compte rendu technique (livrable 4)

Choix d'hébergement

  • Frontend sur GitHub Pages : site statique sans build, gratuit, HTTPS fourni, republié par une GitHub Action à chaque push sur main. Il ne contient aucun secret, seulement l'URL publique de l'API.
  • API sur Scalingo : PaaS européen couvert par le voucher Ynov, déploiement automatique depuis GitHub (il attend que la CI soit verte), logs et rollback en ligne de commande.
  • PostgreSQL en addon Scalingo : même région que l'API, URL de connexion injectée automatiquement dans SCALINGO_POSTGRESQL_URL, donc jamais copiée ni commitée. Le conteneur est éphémère : aucune donnée sur le disque.

Principales configurations

  • Monorepo : PROJECT_DIR=api sur l'app Scalingo pour que le buildpack Python construise le dossier api/.
  • Procfile : web: uvicorn main:app --host 0.0.0.0 --port $PORT ; version de Python dans .python-version ; dépendances figées dans requirements.txt.
  • Variables d'environnement de l'API : SCALINGO_POSTGRESQL_URL (ajoutée par l'addon), CORS_ORIGINS=https://h129hj.github.io.
  • Frontend : la variable de dépôt GitHub API_URL est écrite dans config.js par le workflow de publication.
  • Sécurité : identifiants de la base uniquement côté API, CORS limité au frontend, validation des entrées par Pydantic, requêtes SQL paramétrées, tout en HTTPS, .env ignoré par Git.
  • CI : ruff + 8 tests pytest lancés contre un vrai PostgreSQL dans GitHub Actions.

Problème rencontré et résolution

Premier déploiement de l'API en échec (crashed-error). J'ai créé l'app, ajouté l'addon PostgreSQL et lancé le déploiement aussitôt. Le build passait mais le conteneur plantait au démarrage. Les logs (scalingo --app hugo-tickets-api logs --lines 40) affichaient RuntimeError: DATABASE_URL est requis : la base était encore en création, donc la variable SCALINGO_POSTGRESQL_URL n'existait pas encore, et l'API refuse de démarrer sans base.

Résolution : vérifier que l'addon est running (scalingo addons) et que la variable existe (scalingo env), puis relancer le déploiement : statut success et /health renvoie {"status":"ok"}. Leçon : attendre que la base soit prête avant le premier déploiement, et lire les logs avant de modifier le code.

Redéploiement automatique (étape 6)

Sous-titre de la page modifié (« … suivez sa résolution en temps réel »), commit, push sur main : la GitHub Action a republié le frontend en 21 s et la modification est visible sur l'URL publique sans action manuelle.
